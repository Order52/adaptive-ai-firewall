# Database tier — real 3-tier architecture (2026-10-21)

The lab was extended from 2-tier (WAF → APP) to a genuine **3-tier** architecture
(clients → FW → WAF → APP → **DB**), applied end-to-end on the live lab and verified.
The application now persists business data to PostgreSQL in its own isolated zone.

## What was added

- **DB zone** `10.77.60.0/24` (`SW-DB`, `DB01`) on a **7th OPNsense NIC**
  (opt5 = vtnet6). Firewall rule permits **only `APP01 → DB01:5432`**; the DB
  initiates nothing outbound.
- **DB01** runs **PostgreSQL 16** as a container (`afw/postgres:16`, pre-pulled into
  the golden image like the WAF), data in the `afw-db-data` Docker volume; password
  from host secrets (`~/.config/afw/db/password`), never in Git.
- **Application** gained a real data store (`apps/rental/store.py`): the catalogue,
  users, bookings and reviews live in PostgreSQL when `DATABASE_URL` is set
  (self-migrates + seeds on first start); an in-memory fallback keeps tests/offline
  runs DB-free.

## Apply procedure (this session)

1. Backed up the trained profile v2 + models (`~/afw-backups/pre-dbtier-*`).
2. Rebaked the golden image (added the Postgres image + `psycopg`/`psycopg-pool`);
   `AFW_BAKE_OK`.
3. Gave FW01 a 7th NIC, rebuilt all guests from the new image, created `DB01`/`SW-DB`.
4. Re-provisioned OPNsense (opt5 DB zone + `APP→DB:5432` rule) and the IDS.
5. Deployed all roles incl. the new `db` role; restored profile v2 from backup.
6. Applied the canvas (DB zone) and ran the isolation gate.

## Notes

- Fix applied during rollout: the Postgres container needs a **named Docker volume**
  (`afw-db-data`) rather than a root-owned bind mount, so the data dir inherits the
  image's `postgres` ownership.
- A fresh `afw lab build` creates FW01 with 7 NICs directly; the 6→7 adapter change on
  an existing node required a GNS3 project close/reopen to clear stale switch-port
  allocations (one-time migration artifact, not a topology-definition issue).
