# AI-Adaptive-Firewall — explain it in 5 minutes

A plain-language briefing for talking to your supervisor or teammates. For deep detail see `ARCHITECTURE.md`, `THREAT_MODEL.md`, `SECURITY_AND_LIMITATIONS.md`.

## One sentence

A firewall that watches traffic to a real web app, scores how anomalous each source looks using unsupervised ML, and proposes (or, in bounded cases, applies) enforcement — instead of relying on hand-written signatures.

## The problem it answers

Traditional firewalls/WAFs block known bad patterns (signatures, static rules). They miss novel behaviour and can't adapt without a human rewriting rules. This project asks: can a firewall learn what "normal" looks like for a specific app, flag deviations, and act on them safely — while staying honest about the risk of false positives?

## The pipeline (what actually happens to a packet)

```
Client → OPNsense firewall (FW01) → WAF (reverse proxy) → App → DB
              │                         │
              └────── mTLS telemetry ───┘──→ Controller (CTRL01)
                                              │
                                   windows → detectors → evidence score
                                              │
                                        validator (sanity/safety checks)
                                              │
                                    enforcement (apply / propose / reject)
```

- **Telemetry**: OPNsense, the WAF, and an IDS all stream signed events over mTLS to a central controller.
- **Windowing**: events are grouped per-source into short time windows (request rate, endpoint spread, status codes, etc.).
- **Detectors** (3, run in parallel, trained per-app):
  - `robust_stats` — statistical outlier detection (median/MAD-based).
  - `isolation_forest` — tree-based anomaly detection.
  - `half_space_trees` — online/streaming anomaly detection.
- **Evidence score**: detector outputs are combined into a 0–100 risk score with a confidence band (`elevated`, `high`, etc.) — explicitly described as an *evidence score*, not a probability of attack.
- **Validator**: before anything is applied, sanity-checks the proposal (e.g. never touches protected/management addresses).
- **Enforcement**: depending on mode, either logs the proposal, asks a human to approve it, or auto-applies it within tight bounds — then verifies the change actually took effect on the real backend (read-back, and for outbound geo-blocks, an egress probe too).

## Three modes (the most important slide)

| Mode | What happens |
|---|---|
| **monitor** | Score and record everything. Never act automatically. (Current default — see Limitations.) |
| **assisted** | Same scoring, but proposals need a human to approve/reject before they apply. |
| **auto** | Bounded auto-apply for low-risk, reversible actions only. |

This tiering is the actual safety argument of the project: the ML doesn't get unsupervised authority over a live firewall until its false-positive rate is proven low enough.

## What's real vs. simulated (say this proactively — it's a strength, not a weakness)

- **The pipeline is 100% real**: real mTLS telemetry, real detector math, real OPNsense/WAF API calls, real verification.
- **Country blocking is real** for outbound/inbound traffic in the client zones (USERS, ATTACK) — enforced via actual GeoIP network tables on OPNsense (DB-IP data), not a lookup table pretending to block. Capped at 40,000 networks per direction as a safety bound (the US itself exceeds this and is refused — a genuine, demonstrable safety limit, not a bug).
- **Traffic volume/scenarios are the one deliberately simulated piece**: attack traffic is generated by a scripted benign/attack traffic mixer, not live internet attackers, because running real attack tools against a public target isn't appropriate for a university project. This is disclosed, not hidden.

## Current honest limitation (own this, don't hide it)

The v2 detector model was trained on a narrow set of known traffic patterns. It currently flags a large share of **new, legitimate** users as anomalous too (high false-positive rate on novel-but-benign traffic) — this is exactly why `auto` mode is kept off by default. We proved this live: opening the real app from a genuinely new browser session on the lab's desktop VM triggered the detectors (risk 57.9, "elevated") purely from first-contact traffic, no attack involved. That's a feature of being honest about the system's current maturity, not a cover-up — it's the reason the mode-tiering safety design exists in the first place.

## What makes it "AI-adaptive" specifically

1. **Unsupervised, not signature-based** — detectors learn the app's own normal traffic shape rather than matching known attack strings.
2. **Shadow learning / challenger lifecycle** — new model versions can be evaluated in shadow mode (scoring without acting) before being promoted, so the system can retrain without blindly trusting the new model.
3. **MCP control surface** — the entire system (status, risk assessments, policy history, country blocking, source restriction) is exposed as an AI-agent-controllable interface (Model Context Protocol), so an operator — human or AI assistant — can inspect and act on the firewall conversationally, with every action still going through the same validator/verification path as the dashboard.

## The demo, in one paragraph

Dashboard (live HTTPS, mTLS lab CA) shows Overview/Threats/Policies tabs. We browse the real rental-app from a real desktop VM in the lab (USR01) and watch its traffic get scored live. We block a country (AU) outbound at the real OPNsense level and show a real site become unreachable from that VM, then revoke the block and show it work again. We connect an AI agent over MCP and have it query risk, inspect the live detections, and (if asked) propose a restriction — never applying anything irreversible without the validator's own checks.

## Likely prof questions, short answers

- **"Is this really ML or just thresholds?"** — Three real unsupervised models (stats, isolation forest, streaming trees) combined into one evidence score; shown live via `model_status`/`risk_assessments`.
- **"Why monitor mode, not auto?"** — Measured false-positive rate on novel legitimate traffic is too high right now; shown live, not asserted.
- **"What's actually novel vs. off-the-shelf?"** — Not a new detection algorithm; the contribution is the safety-tiered adaptation pipeline (shadow learning → validated promotion → bounded auto-enforcement) plus making the whole thing operable through an AI agent via MCP with the same safety rails as a human operator.
- **"What would you do with more time?"** — Broaden/retrain the model on more diverse benign traffic to cut the false-positive rate, then graduate from monitor → assisted mode with real approval data.
