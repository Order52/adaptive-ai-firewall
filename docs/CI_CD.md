# CI/CD

Every push and PR is checked the same way a production codebase would be, and
`main` produces a versioned, scanned container image — on top of, not instead
of, the existing lab/evidence discipline (`DEPLOYMENT.md`, `VALIDATION_MATRIX.md`).
What's deliberately out of scope: there is no automatic deployment onto CTRL01
itself. The lab is a physical/virtual GNS3 network behind no public CI runner,
so the last mile (`afw lab deploy`) stays a deliberate, operator-run step —
see `DEPLOYMENT.md` §3. CI/CD here covers the software, not the lab.

## 1. CI (`.github/workflows/ci.yml`) — every push and PR

| Job | What it checks | Command |
|---|---|---|
| `lint` | Style, imports, bugs, security lint (`S` rules), formatting | `ruff check` + `ruff format --check` |
| `typecheck` | Full static typing (`mypy --strict`) | `mypy src` |
| `test` | Unit + integration suite, with coverage | `pytest tests/unit tests/integration --cov=afw` |
| `build` | The package actually builds (sdist + wheel) | `uv build` |

`tests/lab/*` (the `AFW_LAB=1`-gated suite) is **not** run here — those tests
talk to the live GNS3 lab (real OPNsense, real Suricata, real VMs) and have no
meaning on a GitHub-hosted runner. They remain a manual/lab-CI step; see
`VALIDATION_MATRIX.md` for how their evidence is captured instead.

`uv.lock` is committed and CI runs `uv sync --locked`: a dependency bump that
isn't reflected in the lockfile fails CI immediately, by design.

## 2. CodeQL (`.github/workflows/codeql.yml`)

Static security analysis (SAST) on every push/PR to `main`/`engineering-directive`
and weekly on a schedule, independent of `ruff`'s `S` rules. Findings land in the
repo's *Security → Code scanning* tab.

## 3. CD (`.github/workflows/cd.yml`) — `main` and version tags

Runs only after CI has gone green on the same commit (it waits on the CI check
runs rather than re-running them):

1. **Build** the production image from the root `Dockerfile` (multi-stage: `uv`
   resolves and installs into a venv in the builder stage; the runtime stage is
   plain `python:3.12-slim-bookworm`, non-root user, no build toolchain).
2. **Scan** it with Trivy for known CVEs (`CRITICAL`/`HIGH`); results upload to
   the same Security tab as CodeQL. The scan reports but doesn't block the
   pipeline — this is a teaching lab, not a vendor shipping to customers, and
   upstream base-image CVEs shouldn't silently stall every merge.
3. **Push** to `ghcr.io/order52/adaptive-ai-firewall`, tagged `latest` (on
   `main`), the semver tag (on a `vX.Y.Z` tag push), and the short commit SHA
   (always) — so any image can be traced back to the exact commit it came from.
4. **On a version tag**, also cut a GitHub Release with autogenerated notes.

Secrets are never baked into the image: the `Dockerfile`'s header comment shows
the run command, and TLS certs / API tokens / lab credentials are supplied at
container start via volumes and `AFW_*` env vars, exactly as they are on
bare-metal CTRL01.

## 4. Dependabot (`.github/dependabot.yml`)

Weekly PRs for Python dependencies (via `uv.lock`), GitHub Actions versions, and
the Docker base images — so a stale pin is a routine PR, not a surprise.

## 5. What "production" means for a lab project, honestly

The pipeline above is the part that generalizes to any real deployment target:
tests, types, lint, a reproducible build, a scanned and versioned artifact.
What doesn't generalize — because it's the whole point of the project — is
that the *enforcement backend* is a simulated-but-real OPNsense/WAF/app/DB
topology in GNS3, not a cloud VPC. Promoting a build to "run against the lab"
is intentionally still a human running `afw lab deploy`, for the same reason
model promotion requires a human: this is a safety-governed system, and the
last step before touching the enforcement plane is never fully automatic
(`ADAPTATION_DESIGN.md`, `THREAT_MODEL.md` §3.6).
