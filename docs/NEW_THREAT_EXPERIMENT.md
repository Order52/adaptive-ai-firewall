# Learning from a new threat: experiment protocol (master directive §8)

Status 2026-10-29: **protocol and offline machinery ready; not run** (incremental challenger and classifier lifecycle added 2026-10-29). It needs team-run
attack captures of at least three families, with two or more independent runs of the
family that is withheld. No attack traffic is generated by the project itself.

## What it has to show

The point is the difference between two things:

- **Flagging something unfamiliar once.** The novelty and correlation paths can do
  this today.
- **Learning to recognise related future events.** A model that, after one confirmed
  run of a new family, identifies *later, independent* runs of that family. It must do
  so without losing benign generalisation or recall on families it already knew.

## Steps, mechanism and owner

| # | Step | Mechanism | Who | Status |
|---|---|---|---|---|
| 1 | Frozen model + documented known-attack dataset | `KnownThreatClassifier` fitted on the known families' captured runs. Dataset manifests are hashed (`afw ds validate`) | controller | ready |
| 2 | Withheld family introduced with authorized traffic | Team runs the family through the scenario harness (`docs/TEAM_ATTACK_QUICKSTART.md`), which records source, family and timing | **team** | BLOCKED-EXT |
| 3 | Original prediction recorded without prior knowledge | `learn_new_family(...)["introduction_first_seen"]` (frozen has no class for the family) plus the live controller's own assessments for that run | controller | ready |
| 4 | Anomaly and correlation paths assess it | Live: the HTTP risk pipeline, IDS correlation and network novelty in shadow (`/api/network`) during the run | controller | ready (network path in shadow, not yet live-verified) |
| 5 | Labelled only through a trustworthy, independent process | The run's manifest (team's record of what they ran, from where, when) is validated by `afw ds validate`. Labels never come from controller predictions | **team** + validator | BLOCKED-EXT |
| 6 | Confirmed data admitted to a challenger stream | Challenger = frozen's training data + the introduction run's confirmed windows | controller | ready (offline) |
| 7 | Challenger updates and its state changes | Two challengers, both reported: (a) batch refit (`KnownThreatClassifier`, RandomForest) on the appended labelled data; (b) incremental (`incremental.IncrementalThreatClassifier`, river ARF) that learns the introduction run's windows one at a time from `VerifiedLabel`s released after the run's manifest is validated (delayed labels, `LabelGuard`, rehearsal). Checkpoints carry sha256 and label provenance | controller | ready (offline) |
| 8 | Performance on later independent variants | Both models measured on `--test` runs neither saw | controller | ready |
| 9 | Earlier sensitivity and benign generalisation retested | Same unseen runs: benign FPR (Wilson 95 % CI) and per-family recall before/after; regression > 0.05 on a known family makes it ineligible | controller | ready |
| 10 | Promotion only through the gates | `incremental.ClassifierLifecycle`: gate on dataset-disjoint evaluation (benign FPR ≤ 0.02, CI ≤ 0.05; no known-family recall drop > 0.05), named human approver, then probation. **Offline object, unit-tested; not wired to the live controller**, so the classifier never influences a decision | human | offline only |
| 11 | Probation and rollback exercised | `ClassifierLifecycle.observe_benign` rolls back automatically when probation false alerts are clearly above 0.02 (Wilson lower bound), else passes after 500 windows. Unit-tested on SYNTHETIC windows (`tests/unit/test_incremental.py`) | — | offline only |

## Predeclared designation (2026-10-29, before any team attack data exists)

- **Withheld ("new") family: `content_discovery`** (`web-content-discovery`).
  - It produces WAF and behaviour evidence, like the injection family, but it is a
    different activity.
  - Credential guessing is not withheld, because A3 handles it with fixed,
    non-learned rules (ADR-044); a learned "new" result there would be confounded.
- **Known families** for the frozen model: `credential_bruteforce`, `sql_injection`,
  `port_scan`, `ssh_bruteforce`, each with ≥ 1 team run in training.
- **Order.** The `content_discovery` runs are the **last** web family the team records:
  - the first run is the *introduction*;
  - the remaining runs (≥ 2, separate sessions, hours apart) are the *variants*, which
    no model sees before the test.
- **Recorded before the labels exist** (step 3):
  - the frozen classifier's verdicts on the introduction run;
  - the live controller's assessments for ATK01 during that run;
  - the network-novelty shadow verdicts.
  These are exported with `afwc experiment supervised ... --withhold content_discovery`
  (no `--introduce`) and committed before `--introduce` is ever run.
- **Zero-day novelty and later supervised learning are reported separately.**
  - *Novelty*: the share of introduction windows not taken for benign, from the frozen
    model plus the anomaly/correlation paths, with no label.
  - *Learning*: on the variants only, frozen versus each challenger; recall of the new
    family, benign FPR, and known-family recall.
- **Criteria (offline part of the gate):**
  - the challenger's new-family recall on the variants is greater than frozen's, with
    non-overlapping Wilson 95 % CIs;
  - the benign FPR increase is ≤ 0.01;
  - no known-family recall drop > 0.05.
  If this is not met, the result is reported as a negative.

## How to run the offline part

On CTRL01 (`afwc` as in `docs/TEAM_ATTACK_QUICKSTART.md`), after the captures exist:

```
afwc experiment supervised \
  --train <known-family runs + benign runs> \
  --withhold <family> --introduce <first run of that family> \
  --test <later independent runs: the family again + benign + known families>
```

Requirements on the data, checked by the code where possible:

- Introduction and test runs are different datasets (enforced).
- The training data contains no window of the withheld family (enforced).
- Test runs include benign sources from independent sessions and periods (not the
  training users) and at least one known family, so step 9 is measured on unseen data.
- Synthetic manifests are refused unless `--allow-synthetic` is passed. Any result
  that includes synthetic data is reported with `"SYNTHETIC": true`.

## What is not claimed

- The unit tests (`tests/unit/test_supervised.py`) use SYNTHETIC feature vectors. They
  show that the code does the bookkeeping correctly, not that it detects real attacks.
- A family the frozen model maps to "another family" or "unknown" was *not taken for
  benign*. That is different from being recognised, and both numbers are reported
  separately.
